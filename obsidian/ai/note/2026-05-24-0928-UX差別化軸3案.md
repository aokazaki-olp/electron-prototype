# UX 差別化軸 3 案（壁打ち材料）

UI/UX のレビュー会話で「使いやすさの底上げ（skeleton 等）だけ磨いても類似アプリ止まり」という指摘を受け、**このアプリが他になく選ばれる理由を UI 構造に滲ませる**ための方向案を 3 つに整理した。  
記録時点ではどれにも振り切れていない。壁打ち用の素材。

> [!abstract] 結論はまだ
> 案 A/B/C はいずれも採用前提ではない。一つに振るか、A+C のハイブリッドにするか、現状の Workbench 型レイアウトで polish を進めながら走る判断もある。

## 前提整理

| 軸 | 現状の認識 |
|---|---|
| 想定ユーザー | バッチ開発者（書き戻すバッチを Node/Python/Go で書く側）。SF プラットフォームは新規領域。 |
| アプリ位置づけ | バッチ自体ではなく、**バッチ開発を支える dev companion**。 |
| 配布フェーズ | プロトタイプ（社内/限定試用）。マルチビルドの仕組みだけ先行整備。 |
| 既存メモリで決まっている差別化候補 | (1) MCP/Claude 連携 (2) batch dev companion (3) ローカル SQLite ミラー |
| 競合（似たレイアウト） | Salesforce Workbench、Salesforce Inspector Reloaded、VS Code SFDX、Postman+SF API、DataGrip+SF connector |

## 現状 UI と競合の重なり

現在のレイアウトは「左:SObject ブラウザ / 中:SOQL エディタ / 右下:結果+ログ」で、Workbench / Inspector とほぼ同型。**バックエンドには差別化要素がある（MCP/Excel 出力/定義書出力など）が、UI 構造からは伝わらない**。これがレビュー指摘の核心。

---

## 案 A: Claude を副操縦士として常設する

### コンセプト

アプリを起動した瞬間から **Claude（または接続中の Claude Code/Desktop）がペアプロ相手として常駐している** ことが UI 上の主役になる。

### UI 構造

```
┌─────────┬────────────────────────┬───────────────┐
│ SObject │ SOQL Editor (タブ)      │ Claude Panel │
│ Browser │ Result Table            │ (常設)        │
│         │                         │               │
└─────────┴────────────────────────┴───────────────┘
       Status Bar: 🟢 Claude Desktop 接続中 · Account schema 公開中
```

- 右ペインに**常設の Claude パネル**（畳めるが、デフォルトは開いている）
- ステータスバー左下に「**Claude Desktop / Claude Code が MCP で監視中**」表示
- SOQL を書いている最中に「これってこういう意図？」と確認できる
- 結果テーブルを範囲選択 → **右クリックメニュー**：
  - 「Claude にこの結果の解釈を頼む」
  - 「Claude Code に書き戻し TypeScript を生成させる」
  - 「Claude にこの SOQL を最適化させる」
- describe を MCP で常時公開しているため、**Claude 側からも「最新スキーマで」回答できる状態**

### 差別化要素

- Workbench / Inspector には**ない**。MCP 自体が比較的新しい標準で、それを Salesforce ツールに組み込んだ前例は事実上ない
- 「**アプリを起動しているだけで Claude が SF を理解している状態**」になる体験は他に類似なし
- バッチ開発の文脈で、Claude Code でコード書きながらこのアプリで SF 側を確認 → MCP 経由で常時連携、というワークフローが成立する

### コスト/リスク

| 観点 | コメント |
|---|---|
| 実装規模 | 重い。MCP server 化、permission 管理、Claude 側 UI を作るか or 既存 Claude Desktop 任せ |
| API キー問題 | Pro 版（Explorer）はユーザー自身の Claude を使う前提で OK（[[project_ai_integration_strategy]] 通り）。Lite に持ち込まない |
| 失敗モード | MCP が unstable な瞬間に UI 側で「接続中...」が増える。**待ち時間表現の質**が直撃する |
| プロトタイプ枠 | MCP server 部分を別工程に切り出せばプロトタイプの本体に閉じる |

### 既存メモリとの関係

- [[project_ai_integration_strategy]]: Pro 版は MCP 連携、Lite は AI なし — 案 A は Pro 専用機能の中核を担う
- [[project_schema_export_design]]: 定義書出力（MD/JSON）が Claude に食わせる素材。案 A はそれを「**そもそも Claude が常に見ている**」にすることで一段上に持ち上げる

## 案 B: バッチ開発を Workflow として UI に形にする

### コンセプト

「**バッチプロジェクト**」をトップ概念に置く。1 つの書き戻しバッチの開発が、アプリ上で **抽出 → 検証 → 想定 dry-run → rollback 準備** という起承転結の流れとして UI に出る。

### UI 構造

```
┌─ Projects (Sidebar) ────────────────────────────────────────────┐
│ ▼ 売上集計-2026Q2                                                │
│    ├ 抽出 SOQL タブ (3)                                           │
│    ├ 対象 sObject describe スナップショット                       │
│    ├ Dry-run 結果（書き戻し想定）                                  │
│    └ Rollback SOQL（書き戻し前提の取り消し）                       │
│ ▶ 顧客マスタ更新-2026Q1                                           │
│ + 新規プロジェクト                                                 │
└──────────────────────────────────────────────────────────────────┘
```

- 起動画面が「最近のプロジェクト一覧」（VS Code の Recent Projects のような感覚）
- プロジェクト = 「**SOQL タブ群 + 対象 sObject describe スナップショット + dry-run ログ + rollback SOQL**」のひとまとまり
- バッチが触る sObject の describe を**スナップショット**として保存（後で「あの時の Account はこのフィールド構成だった」が見える）
- 「**この SOQL で 12,034 件取れる → 書き戻し対象 → 想定 update 件数 12,034 → rollback SOQL は SELECT Id, Name FROM Account WHERE LastModifiedDate >= ...**」のような一連の流れがプロジェクトページに表示される

### 差別化要素

- Workbench / Inspector は**単発操作ツール**。これは **workflow ツール**。違うカテゴリになる
- バッチ開発者が「**この sObject にこの順序でこの SOQL を流す予定**」を**アプリ内で構造化**できる
- 後でバッチ実装側（Node/Python/Go）から見たときの「**設計書として参照する**」相手になりうる

### コスト/リスク

| 観点 | コメント |
|---|---|
| 実装規模 | 構造改修が要る。現在の「タブ+1 active profile」モデルから「Projects + active project + tabs」へ。store の階層が一段増える |
| 概念導入の重さ | ユーザーに「Project」概念を新しく覚えてもらう必要がある。Solo 開発でも overhead |
| スコープ判断 | バッチ開発を**専門に**するなら大正解、汎用 SF クライアントとしては過剰 |
| プロトタイプ枠 | 概念導入はプロトタイプ後半でも遅くない。先に MVP で当てる感触を見たい |

### 既存メモリとの関係

- [[project_app_genesis_data_enrichment]]: 起点は「書き戻すバッチの開発」 — 案 B はその文脈に最も忠実
- [[project_batch_is_external_rest]]: 外部 REST 実装である前提 → アプリ側は workflow 管理に専念できる

## 案 C: ローカル SQLite ミラーを"見える化"する

### コンセプト

org のデータと describe を**ローカル SQLite に pull して持つ**ことを、UI の主役にする。「**org の中で SOQL を叩く道具**」ではなく「**ローカルに連れてきた org を相手にする道具**」になる。

### UI 構造

```
┌─ Local Mirror Status ───────────────────────────────────────────┐
│ 🔄 Pull org   最終取得: 2026-05-24 09:28                          │
│ ─────────────────────────────────────────────────────────────── │
│ Account      12,034 行  describe ✓  最終更新 09:28                │
│ Contact      45,128 行  describe ✓  最終更新 09:28                │
│ Opportunity   3,210 行  describe ✓  最終更新 09:28                │
│ Custom__c       142 行  describe ✓  最終更新 09:28                │
│ + 追加 sObject                                                    │
└──────────────────────────────────────────────────────────────────┘
   ↓ クリックで通常の SObject Browser に降りる
```

- 起動画面が空テーブルじゃない。**「現在ローカルにあるもの」一覧**
- 「**Pull org**」ボタンで一括ダンプ。進捗バーが**正面で動く**（待ち時間自体が体験の一部になる）
- SOQL は**ローカル SQLite に対しても実行可能**。SF 側との diff も見える
- ローカルなので**オフラインでも触れる、grep できる、git にコミットして変更追跡できる**
- 定義書出力もローカルから生成（[[project_schema_export_design]] と直結）

### 差別化要素

- これも Workbench / Inspector に**ない**体験。彼らは「org に都度問い合わせる」前提
- バッチ開発で「**ある時点の SF 側の状態をスナップショットして再現性のあるテストを書きたい**」という現実のニーズに刺さる
- AI 連携（案 A）と相性が良い：**ローカルにあるから Claude にも安全に大量データを見せられる**

### コスト/リスク

| 観点 | コメント |
|---|---|
| 実装規模 | SQLite 連携、JSON→SQLite 変換、差分管理。[[project_schema_to_sqlite_ecosystem]] で「変換器は別ツール」と決めているので、その境界を改めて引き直す必要がある |
| ストレージ | org 全件ダンプはサイズが膨らむ。pull 対象を絞る UI が必要 |
| 同期境界 | 「ローカルと SF どっちが正？」のメンタルモデル設計が要る。**常にローカルが古い前提**を UI に出すか |
| プロトタイプ枠 | extract 部分はアプリの責務、変換は別 — の境界を保てば収まる |

### 既存メモリとの関係

- [[project_schema_to_sqlite_ecosystem]]: 将来構想として整理済み。**今の JSON 設計はこの用途を支える前提で固めた**とある — 素地はある
- [[project_schema_export_design]]: 定義書出力（MD/JSON）はそのままローカルミラーの一部として再解釈できる

## 3 案の比較

| 観点 | 案 A: Claude 副操縦士 | 案 B: バッチ Workflow | 案 C: ローカルミラー |
|---|---|---|---|
| 差別化の鋭さ | ◎（MCP 時代の本命） | ○（workflow ツールという別カテゴリ） | ○（オフライン + diff という別軸） |
| 実装規模 | 重 | 中〜重（構造改修） | 中（境界次第） |
| プロトタイプ適合度 | △（MCP は別工程切り出し前提） | △（概念導入は MVP の後でも） | ○（extract 単位で先行可能） |
| 既存方針との整合 | ◎ ([[project_ai_integration_strategy]]) | ◎ ([[project_app_genesis_data_enrichment]]) | ◎ ([[project_schema_to_sqlite_ecosystem]]) |
| 単独で成立 | ○ | ○ | ○ |
| 他案と組合せ | A+C は相性◎ / A+B は工数膨大 | A+B は重い / B+C は概念二重化 | A+C 推し / B+C は概念二重化 |
| Lite 版への流用性 | × ([[project_ai_integration_strategy]] で Lite は AI なし) | △（簡易 workflow なら可） | ○（[[project_lite_scope_flexibility]] と整合） |

## ハイブリッドの本命候補：案 A + 案 C

最も現実的で既存メモリ全体と一直線になるのは **案 A（Claude 副操縦士）+ 案 C（ローカルミラー）**。

理由：

- ローカルにデータがある → Claude に安全に渡せる（権限・量・速度のすべてが解決）
- describe を MCP 公開する基盤はローカルミラー側に作ればよい
- [[project_ai_integration_strategy]] [[project_schema_to_sqlite_ecosystem]] [[project_schema_export_design]] が**一本の線で繋がる**
- Lite 版に AI を外して **C だけ提供**するという分岐が綺麗（[[project_lite_scope_flexibility]] と整合）
- バッチ開発の文脈では「ローカルで安心して試して、AI と相談して、確信を持ってから本番 org に流す」体験になる

## 案 B を一旦置く理由

案 B は魅力的だが、

- 概念導入（Project トップ階層）が重い
- バッチ開発の workflow 構造化は、まずユーザー自身が**何を求めているか**を A+C で使いながら見えてくる
- A+C で出てきた「**よく使う SOQL タブ群を 1 単位で扱いたい**」という気持ちが固まってから B に進む方が、無理がない

将来「**プロジェクト**」概念は A+C の上に乗せられる。順序の問題。
